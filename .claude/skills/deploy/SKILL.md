# Docker & deployment

`docker compose up -d --build` brings up db, keycloak, **two** backend replicas, **two** frontend replicas and nginx (`.env.example` → `.env` for credentials; defaults are dev-only). The rubric asks for **three**: the third lives in `docker-compose.three.yml`, applied on top (`docker compose -f docker-compose.yml -f docker-compose.three.yml up -d`), because three JVMs at 640 MB do not fit on every machine. `README.md` has the URLs and the smoke tests.

- **nginx is the only published service** (`:80`), as the plan requires: db and the backends have no host ports. It balances `/` across `frontend-1/2` and `/api` across the backend replicas and proxies `/auth` to Keycloak, so the browser sees **one origin** and no CORS config is needed anywhere — the same shape as the Vite proxy in dev, which is why the frontend is built with `VITE_API_URL=/api` and `VITE_KC_URL=/auth` (Vite bakes those at build time, hence the Dockerfile build args).
- **The Keycloak issuer is the fragile part.** Keycloak runs with `KC_HTTP_RELATIVE_PATH=/auth`, and `KC_HOSTNAME` must be the full public URL **including that path** (`http://localhost/auth`): given only the host, Keycloak advertises its endpoints without `/auth` and the `iss` claim no longer matches what the backend validates. The backend therefore gets two properties: `issuer-uri` with the **public** URL (what travels in the token) and `jwk-set-uri` with the **internal** one (`http://keycloak:8080/auth/...`), so key fetching never depends on external DNS. Changing `PUBLIC_URL` changes both at once.
- **Replicas with explicit names** (not `deploy.replicas`) so nginx's `upstream` lists them one by one and a replica can be stopped to demonstrate balancing. That `upstream` block is **not** in `nginx/nginx.conf`: it is `nginx/upstream-2.conf` (mounted as `conf.d/00-upstream.conf`) or `nginx/upstream-3.conf`, which the override mounts over the same target — Compose merges `volumes` by target, so the override's file wins and the rest of the nginx config is shared. The frontend's own upstream is a third file (`nginx/upstream-frontend.conf` → `conf.d/01-upstream-frontend.conf`) precisely because it does *not* vary between the two compose files; the plan asks for a single frontend instance, and there are two so the SPA's balancing is demonstrable too. nginx resolves upstream hostnames at startup, so it will not boot if a listed replica's container does not exist, which is why the override also adds `backend-3` to its `depends_on`; `log_format siga` records `$upstream_addr`, so `docker compose logs nginx` shows which replica served each request. Verified: 12 requests split 4/4/4, and with `backend-2` stopped every request still returns 200 (`proxy_next_upstream` retries, then `max_fails` takes it out of rotation).
- **The Swagger trap**: springdoc serves the UI at `/swagger-ui.html` and the spec at `/v3/api-docs`, both **without a trailing slash**. nginx's regex for those routes must therefore not require one (`^/(swagger-ui|v3/api-docs|swagger-resources|webjars|actuator)`, the same list `SecurityConfig` leaves public). With a pattern that ended in `/`, those two URLs fell through to `location /` and the browser got the SPA's `index.html` **with a 200**, so a status-code-only smoke test does not catch it — check the body.
- Because the schema is `ddl-auto=update`, **every other replica waits for backend-1 to be healthy** (`depends_on: service_healthy`) instead of racing on the same DDL. The health check needs `curl`, which is why the runtime image installs it.
- **The image build does not run the tests**: they need a Docker daemon for Testcontainers, so running them inside the build would mean Docker-in-Docker. CI runs them before building.
- Keycloak starts with `--import-realm` from `keycloak/import/`, where `siga-realm.json` is already exported (realm, the three roles, the `siga-frontend` client and the three demo users with their password hashes), verified end to end through port 80. Empty that directory and the realm does not exist: every login fails with a 404 on the realm. `keycloak/README.md` has the re-export command (the server must be stopped first) and what the realm must contain. Its `/opt/keycloak/data` is a named volume, so users created through the console survive a recreation of the container.
- **`deploy/seed.sh`** fills an empty database through the API with the project's Appendix A (3 careers, 72 subjects with prerequisites, teachers, students, 2025-2 closed with history and 2026-1 open). It needs all three users' passwords by environment variable, because the roles are not interchangeable: the student enrolls (the backend takes them from the token), the responsible teacher grades, the admin closes. Two traps it documents by construction: every section of a period gets a distinct day+module slot from one shared counter — a per-career reset makes a teacher collide with themselves across plans — and the helper functions log to **stderr**, because their stdout is the id that the caller reads with `$(...)`.
- **`deploy/simulate.ps1`** turns that catalog into a running institute, also through the API and also role by role: it creates `2025-1`, enrolls a 15-student cohort in semester 1, grades it (with a planned set of failures), **closes it** so the academic history is written by the system's own closure, and then fills `2026-1` with semesters 1 and 2 of all three plans (36 sections, 12 active teachers, 28 students, 162 enrollments, grades left deliberately half-done). Three things it relies on: all sections of **one plan in one period** get disjoint day+module slots out of the 30-slot grid (5 days x 6 modules), which is what makes every cohort timetable, every repeater mixing semesters, and every single-plan teacher valid by construction; a semester-sorted **prefix** of `enrollments/available` satisfies the lower-semesters-first rule for free; and it loads the slots already in use before allocating, so it coexists with whatever `seed.sh` built. Two PowerShell traps it documents by construction: `return $hashset` **enumerates** the collection (an empty one comes back as `$null`, a full one as an array with no `.Add()`), and the 6-subject cap counts what the student already has, so a second run must enroll `6 - already` or the backend rightly answers 409. `-SkipPast` leaves `2025-1` alone.
- **CD** is the `deploy` job of that same workflow: it SSHes into the EC2 box (`EC2_HOST`/`EC2_USER`/`EC2_SSH_KEY` secrets) and runs **`deploy/update.sh`**, gated on `needs: [images]` and `main` only, under a `concurrency` group so two pushes cannot deploy at once. The script replaces **one replica at a time**, waiting for each to report `healthy` before touching the next, so nginx always has a sound backend and the demo never goes dark mid-deploy — the replicas earn their keep here, not just in the rubric. It never touches volumes, so demo data survives every deploy. The friction to know about: GitHub's runners have dynamic IPs, so SSH-based deploys mean opening port 22 to `0.0.0.0/0` (key-only auth); `deploy/aws.md` says so plainly and notes that closing it again just means updating by hand with the same script.
- **CI** is `.github/workflows/ci.yml`: unit tests → `mvnw verify` (integration + coverage gate) → `npm ci`/lint/build → images pushed to Docker Hub, the last job gated on both suites and skipped on pull requests. It needs one secret, `DOCKERHUB_TOKEN`; the Docker Hub user is a plain `env` value in the workflow. The workflow `chmod +x mvnw` before running it, because the repository is created from Windows and the executable bit may not survive the commit.
- **Only `PUBLIC_URL` changes between localhost and the cloud.** The frontend is built with relative URLs, so the same image serves any host; `deploy/aws.md` is the EC2 walkthrough (t3.medium amd64 — the images are amd64 — security group with 22 and 80, `docker compose pull && up -d --no-build`, measured footprint ~1.5 GB). Each backend is capped at `mem_limit: 640m` (real use ~285 MB) and Keycloak at 768m (~517 MB).
